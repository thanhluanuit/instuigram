# Rails 8.0 → 8.1.3.x Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the app from Rails 8.0.5.1 to Rails 8.1.3.x, with `config.load_defaults` bumped to `8.1`, all existing tests/linters/scanners green, and no silently-dropped config (the known `app:update` gotcha from the 7.2→8.0 hop).

**Architecture:** This is a single-minor-version hop (8.0 → 8.1), so it's one stage, not a multi-step staged upgrade — bump the gem constraint, run `bundle update rails`, run `bin/rails app:update` and reconcile its diff by hand against this app's deliberate overrides, bump `load_defaults`, regenerate `schema.rb` (8.1 sorts columns alphabetically by default), then verify with the full local + CI-equivalent check suite.

**Tech Stack:** Ruby 3.3.11 (unchanged — Rails 8.1 requires ≥3.2, no bump needed), Rails 8.1.3.x, Bundler 2.4.22, PostgreSQL (Homebrew locally), Elasticsearch 8.x (`docker compose up -d`, this project's existing convention — do not introduce Docker for anything else), Redis (Homebrew locally, `:null_store` in test so not needed for the test suite itself).

**Spec:** No separate spec doc — the "spec" is the version bump itself plus the upgrade-safety practices already codified in `CLAUDE.md` (staged-upgrade convention, the documented `app:update` gotcha) and this plan's own research (see Task 1 notes) into the official Rails 8.1 release notes and upgrade guide.

## Global Constraints

- Ruby stays at 3.3.11 — do not bump it as part of this upgrade (Rails 8.1 only requires ≥3.2; a Ruby bump is a separate, deliberate decision with its own `mutex_m` tradeoff noted in `CLAUDE.md`).
- Review every file `bin/rails app:update` touches line-by-line before accepting it — the 7.2→8.0 hop silently dropped `require_master_key`, `js_compressor`, `assets.compile`, and `public_file_server` from `production.rb` because Rails 8's template assumes Propshaft/Kamal defaults this app doesn't use. Assume 8.1's template can do the same.
- Never use `git add -A` / `git add .` for this work — the working tree already has unrelated in-progress changes (staged `docker-compose.yml`, modified `README.md`, untracked `asvs-audit/`, `performance-review-report/`, `.claude/settings.json`) that must not get swept into these commits. Stage only the exact files each task lists.
- Keep the diff minimal: `bundle update rails` (not a blanket `bundle update`), so unrelated gems don't churn.
- Every task's commit must leave `bin/rails test`, `bundle exec rubocop`, `bundle exec brakeman`, and `bundle exec bundle-audit check --update` green — these are exactly CI's gates (`.github/workflows/ci.yml`).
- `export LDFLAGS="-Wl,-ld_classic"` before any `bundle install`/`bundle update` on this machine — modern Xcode's linker otherwise breaks native gem compilation (nio4r, ffi, pg), per `CLAUDE.md`'s documented gotcha.

### Task 2: Run `bin/rails app:update` and reconcile the diff by hand

**Files:**
- Modify: `config/application.rb:12` (`config.load_defaults 8.0` → `config.load_defaults 8.1`)
- Modify/create: whatever `bin/rails app:update` proposes touching (`config/environments/{development,production,test}.rb`, `config/initializers/*`, `bin/*`, `config/boot.rb`, etc.) — reviewed and reconciled by hand, not accepted wholesale.
- Create (temporarily): `config/initializers/new_framework_defaults_8_1.rb` (generated by `app:update`; see Step 4).

**Interfaces:**
- Consumes: Rails 8.1.3.x from Task 1.
- Produces: an app running under `load_defaults 8.1` with every 8.0-era deliberate override (documented inline in `config/environments/production.rb`, e.g. `require_master_key`, `js_compressor`, `assets.compile`) still intact.

- [ ] **Step 1: Run the generator interactively**

```bash
bin/rails app:update
```

For each file it proposes changing, don't blanket-accept (`a`). Use `d` to view the diff for anything under `config/`, `bin/`, or `Gemfile`, then decide per file:
- Accept (`y`) for genuinely new boilerplate this app has no reason to diverge from (e.g. a new `bin/*` script, a brand-new initializer this app doesn't already customize).
- Reject (`n`) for any file where the diff would remove or alter a setting this app deliberately set — cross-check every proposed change to `config/environments/production.rb` against the inline comments already there (`require_master_key`, `js_compressor`/`assets.compile` for the Sprockets pipeline, `assume_ssl`, `force_ssl`, `cache_store`, `active_record.attributes_for_inspect`). If the generator wants to remove or default any of these, reject and reapply the app's version by hand afterward instead.

- [ ] **Step 2: Diff every touched file against git history**

```bash
git status
git diff -- config/ bin/ Gemfile
```

For every changed file, confirm no line silently disappeared that this app relies on. Specifically re-check `config/environments/production.rb` still contains, verbatim:

```ruby
config.require_master_key = true
config.assets.js_compressor = :terser
config.assets.compile = false
```

If `app:update` regenerated `config/environments/production.rb` without these (the exact failure mode from the 7.2→8.0 hop), reapply them by hand with `Edit`, preserving the existing explanatory comments already in the file.

- [ ] **Step 3: Bump `load_defaults`**

In `config/application.rb`, change:

```ruby
config.load_defaults 8.0
```

to:

```ruby
config.load_defaults 8.1
```

- [ ] **Step 4: Review and retire the new-framework-defaults initializer**

`app:update` generates `config/initializers/new_framework_defaults_8_1.rb` with every 8.1 default commented out, letting you opt in gradually. Read it fully — nothing this app currently checked out found any 8.1-specific `load_defaults` behavior change beyond the ones already listed in this plan's Global Constraints research (schema column sorting, the Sidekiq adapter deprecation, and a handful of removed/deprecated APIs this app doesn't use — no `azure` storage, no SQLite `:retries`, no MySQL unsigned columns, no semicolon query-string parsing, no multi-path routing). Since Task 3's `load_defaults 8.1` already takes effect without opting into anything from this file, delete it once satisfied nothing in it applies:

```bash
rm config/initializers/new_framework_defaults_8_1.rb
```

- [ ] **Step 5: Boot and smoke-check**

```bash
bin/rails runner 'puts "boots ok under 8.1 defaults"'
RAILS_ENV=production SECRET_KEY_BASE=dummy bin/rails runner 'puts Rails.application.config.require_master_key' 2>&1 | tail -5
```

Expected: first command prints cleanly with no deprecation warnings. Second command's output (or its failure mode, since `RAILS_MASTER_KEY`/`master.key` won't be present here) should reflect `require_master_key = true` still being configured — the point is confirming the setting is still present in the loaded config, not a full production boot.

- [ ] **Step 6: Commit**

```bash

git status  # confirm nothing unrelated (docker-compose.yml, README.md, asvs-audit/, performance-review-report/, .claude/settings.json) got staged

```

**Interfaces:**

- Produces: a `schema.rb` whose column order matches what a fresh `db:schema:load` under 8.1 would produce, matching what CI's `bin/rails db:schema:load` step will do.

- [ ] **Step 1: Regenerate the schema**

```bash

```

Expected: `db/schema.rb` changes — columns within each `create_table` block reordered alphabetically. No table, column, index, or foreign key should be added/removed/retyped; only in-block ordering changes.

- [ ] **Step 2: Diff and sanity-check**

```bash

```

Confirm the diff is pure reordering (same column names/types/options per table, just resorted) — if anything besides order changed, stop and investigate before proceeding (that would indicate a migration/schema drift unrelated to this upgrade).

- [ ] **Step 3: Reload the test database from the new schema and confirm the app still reads/writes correctly**

```bash

RAILS_ENV=test bin/rails db:schema:load

```

Expected: schema load succeeds, model-layer tests pass unchanged (column reordering is representational only — Active Record addresses columns by name, not position).

- [ ] **Step 4: Commit**

```bash

```
